# 3.3.2 Labels or Instructions

WCAG 2.2 · Level **A**

A practical summary in our own words; the exact obligations are set by the normative text and its definitions.

## Applicability

The content requires user input.

## What is required

Provide labels or instructions sufficient for input.

## How to test

1. Check visible labels, required status, format and constraints before input.
2. Compare them with the expected values.

**Expected result:** Provide labels or instructions sufficient for input. All applicable states and normative exceptions have been checked.

**Fails when:** A field requires a special format, but the user learns it only after the input is rejected.

## How to fix

Provide a visible label and the needed instructions in advance.

## Example

**Before:** The "Date" field requires the day and month in an unusual format with no explanation.

**After:** The expected format and an original example are given.

## Exceptions and false positives

An accessible name on its own does not always replace an instruction for all users; unnecessary instructions are not required for obvious input.

## Automation and evidence

A tool can collect candidates and measurements; the verdict depends on applicability, content, exceptions and observed behavior. The absence of an automated signal is not a pass. The main conclusion requires a person to carry out the scenario, or an observed interactive run; a static DOM alone is not enough.

- URL/route, interface state, date, sign-in method and the steps tested.
- Viewport in CSS px, zoom level, input method, user agent, and assistive technologies if used.
- The specific element/media segment/process step, reproducible observations and the actual result.
- The normative condition of 3.3.2, the exceptions checked, and an explanation of the barrier to the user.
- For this test, record: Check visible labels, required status, format and constraints before input; compare them with the expected values.
