# 3.3.1 Error Identification

WCAG 2.2 · Level **A**

A practical summary in our own words; the exact obligations are set by the normative text and its definitions.

## Applicability

An input error is automatically detected.

## What is required

Identify the item in error and describe the error in text.

## How to test

1. Submit invalid and empty values.
2. Check the text, its association with the field and the accessibility of the message.

**Expected result:** Identify the item in error and describe the error in text. All applicable states and normative exceptions have been checked.

**Fails when:** An invalid field is marked only with a border, without a text description.

## How to fix

Provide a clear text message that identifies the field.

## Example

**Before:** After submission the field is highlighted with no explanation.

**After:** "End date is earlier than start date" is associated with the date field.

## Exceptions and false positives

The criterion does not require every possible error to be detected automatically; it governs input errors that are already detected.

## Automation and evidence

A tool can collect candidates and measurements; the verdict depends on applicability, content, exceptions and observed behavior. The absence of an automated signal is not a pass. The main conclusion requires a person to carry out the scenario, or an observed interactive run; a static DOM alone is not enough.

- URL/route, interface state, date, sign-in method and the steps tested.
- Viewport in CSS px, zoom level, input method, user agent, and assistive technologies if used.
- The specific element/media segment/process step, reproducible observations and the actual result.
- The normative condition of 3.3.1, the exceptions checked, and an explanation of the barrier to the user.
- For this test, record: Submit invalid and empty values; check the text, its association with the field and the accessibility of the message.
