# 2.1.2 No Keyboard Trap

WCAG 2.2 · Level **A**

A practical summary in our own words; the exact obligations are set by the normative text and its definitions.

## Applicability

Focus can be moved into a component using the keyboard.

## What is required

Provide a way to move focus away using the keyboard; if the way out is non-standard, tell the user what it is.

## How to test

1. Enter every widget and nested region.
2. Try moving out forward and backward.
3. Check the instructions for non-standard keys.

**Expected result:** Provide a way to move focus away using the keyboard; if the way out is non-standard, tell the user what it is. All applicable states and normative exceptions have been checked.

**Fails when:** Focus enters a calendar and never returns to the page.

## How to fix

Fix the focus loop; provide a standard way out or explain the non-standard one.

## Example

**Before:** The date grid captures Tab permanently.

**After:** Tab moves out to the next field.

## Exceptions and false positives

Keeping focus inside an open modal dialog is acceptable when there is an accessible keyboard way to close it and exit the modal state.

## Automation and evidence

A tool can collect candidates and measurements; the verdict depends on applicability, content, exceptions and observed behavior. The absence of an automated signal is not a pass. The main conclusion requires a person to carry out the scenario, or an observed interactive run; a static DOM alone is not enough.

- URL/route, interface state, date, sign-in method and the steps tested.
- Viewport in CSS px, zoom level, input method, user agent, and assistive technologies if used.
- The specific element/media segment/process step, reproducible observations and the actual result.
- The normative condition of 2.1.2, the exceptions checked, and an explanation of the barrier to the user.
- For this test, record: Enter every widget and nested region; try moving out forward and backward; check the instructions for non-standard keys.
