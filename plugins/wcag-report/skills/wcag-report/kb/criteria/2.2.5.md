# 2.2.5 Re-authenticating

WCAG 2.2 · Level **AAA**

A practical summary in our own words; the exact obligations are set by the normative text and its definitions.

## Applicability

A session expires during an activity, after which sign-in is required; AAA.

## What is required

After re-authenticating, the user can continue the activity without loss of data.

## How to test

1. Fill in several steps.
2. Wait for the session to expire.
3. Sign in again.
4. Check the values and the current step.

**Expected result:** After re-authenticating, the user can continue the activity without loss of data. All applicable states and normative exceptions have been checked.

**Fails when:** Signing in again deletes a long unfinished request.

## How to fix

Save the state and restore it after authentication.

## Example

**Before:** The report text is lost after the session expires.

**After:** Signing in returns the same text and step.

## Exceptions and false positives

Having a time extension under 2.2.1 does not prove that data is preserved after re-authentication.

## Automation and evidence

A tool can collect candidates and measurements; the verdict depends on applicability, content, exceptions and observed behavior. The absence of an automated signal is not a pass. The main conclusion requires a person to carry out the scenario, or an observed interactive run; a static DOM alone is not enough.

- URL/route, interface state, date, sign-in method and the steps tested.
- Viewport in CSS px, zoom level, input method, user agent, and assistive technologies if used.
- The specific element/media segment/process step, reproducible observations and the actual result.
- The normative condition of 2.2.5, the exceptions checked, and an explanation of the barrier to the user.
- For this test, record: Fill in several steps; wait for the session to expire; sign in again; check the values and the current step.

## Code patterns

The scenario is given above. Code alone is not enough to test media, processes and semantics.
