# 3.3.3 Error Suggestion

WCAG 2.2 · Level **AA**

A practical summary in our own words; the exact obligations are set by the normative text and its definitions.

## Applicability

An error is detected automatically and a way to correct it is known.

## What is required

Suggest a correction, unless this would jeopardize the security or purpose of the content.

## How to test

1. Submit invalid data.
2. Check how specific the suggestion is and whether the error can be corrected.

**Expected result:** Suggest a correction, unless this would jeopardize the security or purpose of the content. All applicable states and normative exceptions have been checked.

**Fails when:** The message "Error" does not explain the known rule for a valid value.

## How to fix

State the allowed range, format or another specific way to correct the input.

## Example

**Before:** The value 47 is rejected with the word "Invalid".

**After:** "Enter a number from 1 to 30".

## Exceptions and false positives

Do not disclose information that would jeopardize security or purpose. Do not require a suggestion if the way to correct the error is not known.

## Automation and evidence

A tool can collect candidates and measurements; the verdict depends on applicability, content, exceptions and observed behavior. The absence of an automated signal is not a pass. The main conclusion requires a person to carry out the scenario, or an observed interactive run; a static DOM alone is not enough.

- URL/route, interface state, date, sign-in method and the steps tested.
- Viewport in CSS px, zoom level, input method, user agent, and assistive technologies if used.
- The specific element/media segment/process step, reproducible observations and the actual result.
- The normative condition of 3.3.3, the exceptions checked, and an explanation of the barrier to the user.
- For this test, record: Submit invalid data; check how specific the suggestion is and whether the error can be corrected.
